# Task 3 — Financial report per court

Django + PostgreSQL implementation of a per-court financial report. Five models (Branch, Court, Tag,
Booking, Payment) store confirmed bookings, their successful payments and their many-to-many tags;
two services compute the count of confirmed bookings, the collected amount and distinct tag names for a
date range on booking `start_date`, including courts with no bookings. A naive N+1 version is kept next
to an optimized, paginated version so the query reduction can be measured.

## Run

```bash
cd task03_court_report
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
set -a; . ../.env; set +a
DJANGO_SETTINGS_MODULE=court_report.settings .venv/bin/python -m django ensure_db
DJANGO_SETTINGS_MODULE=court_report.settings .venv/bin/python -m django migrate --noinput
DJANGO_SETTINGS_MODULE=court_report.settings .venv/bin/python -m django seed_bookings --bookings 100000 --reset
```

`ensure_db` calls `reports.db_utils.ensure_database()`: it uses psycopg with the documented env vars,
creates `task03` if it is absent and is a no-op if it already exists. `tests/conftest.py` calls the
same helper in `pytest_sessionstart`, so a fresh checkout can run both commands in either order.
`seed_bookings` defaults to 100,000 bookings. It uses batched `bulk_create` (5,000 per batch), 20 courts,
10 tags, two payments and two tag links per booking. It is idempotent: a second run without `--reset`
reports `Already seeded; pass --reset to replace the dataset.` and writes nothing; `--reset` deletes
the previous bookings (and cascaded payments/tag links) before inserting. Settings read `POSTGRES_HOST`,
`POSTGRES_PORT`, `POSTGRES_USER` and `POSTGRES_PASSWORD` from the environment; the socket directory and
empty port/password from `../.env` are passed straight to Django. Database name is `task03`.

### Query counts

Exact counts are asserted in the tests, not estimated in prose:

- 50 courts × 2 confirmed bookings × 1 payment × 3 tags: optimized **4**, naive **252** =
  `2 + 50 courts + (100 bookings × 2 relation queries)`.
- 100k seed, 50-court page, 2026-06-01…2026-06-07: 20 courts and 1,680 confirmed bookings in range,
  so naive **3,382** = `2 + 20 + 2 × 1,680`; optimized **4**. Both numbers are printed by the
  benchmark command below (`query_counts()`).

### Why the sums do not multiply

The optimized service never joins `tags` to `payments`. It runs one grouped query over
bookings × payments (`Count(DISTINCT b.id)`, `SUM(p.amount) FILTER (WHERE p.successful)`) and a separate
`DISTINCT` query over bookings × tags. A single join would repeat every payment once per tag.

### Which indexes the plans actually use

- `BEFORE-bookings`: `booking_court_start_idx` (single-court lookup by court + date range).
- `BEFORE-payments`: the FK index `reports_payment_booking_id_64908cc3`, **not**
  `payment_booking_success_idx`.
- `BEFORE-tags` and `AFTER-tags`: the composite unique index
  `reports_booking_tags_booking_id_tag_id_28903b39_uniq`; `reports_tag` is small enough to seq scan.
- `AFTER-aggregates` and `AFTER-tags`: `booking_start_idx` (the whole 20-court page is one `IN` list,
  so the planner prefers the date-only index over `booking_court_start_idx`).
- `payment_booking_success_idx` and `booking_court_start_idx` are **unused by the two AFTER plans**.
  They are kept because the spec asks for suggested indexes and the single-court BEFORE plan does use
  `booking_court_start_idx`; no claim is made that they accelerate the page report.
- The defect exposed by the plans is the **3,382 client round trips** of the naive service versus **4**
  for the set-based service, not a slow individual index lookup.

1. **Untagged bookings — reproduced and fixed.** Red run of
   `tests/test_round2.py::test_spec_untagged_booking_does_not_add_none_tag` on the old code failed at

2. **Exact query counts — not reproduced as a failure.** The old numbers were correct; the gap was that

   `tests/test_round2.py::test_spec_exact_query_counts_and_all_row_values_50_courts` passes with exact

3. **Pagination — reproduced and fixed.** Old code raised
   `django.core.paginator.EmptyPage: That page number is less than 1` for `page=0`, and
   `tests/test_round2.py::test_spec_page_size_is_capped_at_100` failed with `assert 120 == 100`. Fix:
   `_court_page()` clamps pages into `[1, num_pages]` and caps `page_size` at 100 for both services.
4. **Mutating the old infra-only checks — not reproduced as a code bug.** The finding was a process
   gap, not a failing behaviour: the three old mutations (database bootstrap, benchmark selector,
   README) never exercised business logic. They were replaced by the five business mutations in the
   table above; each was run and confirmed to fail a named test, then reverted.
5. **Correlated seed — reproduced and fixed.** Before the fix,
   `tests/test_round2.py::test_spec_seed_decouples_court_from_confirmed` failed with

## Assumptions

- "Confirmed booking" means `Booking.confirmed = True`; "collected" means `Payment.successful = True`.
  The sample (1 booking, 200 of 200 rial collected, 30 failed excluded) pins this reading.
- The spec's "admin page" need is interpreted as the report service/query such a page would call.
  AGENTS.md forbids building admin/frontend extras, so no Django admin UI or template was added.
- Amounts use `DecimalField(14, 2)` (rial), never `float`. `USE_TZ=True`, `TIME_ZONE="UTC"`; the report
  filter uses `DateField` values, so no naive datetimes occur.
- The date filter is inclusive at both ends (`[from, to]`). The initial boundary test contradicted its
  own fixture by expecting zero on a date where it had just created a confirmed booking; it was corrected
  to assert 1 on that boundary and 0 on a date with no booking. No assertion was weakened.
- ⚠ The spec does not say what an out-of-range page should do. We chose to clamp to the first/last
  page (and to cap `page_size` at 100) rather than raise, so admin-style callers always get a page.
- ⚠ A full month on the 50-court page makes the deliberately N+1 service issue far more than Django's
  9,000-query capture buffer (`Limit for query logging exceeded, only the last 9000 queries will be
  returned.`). The documented EXPLAIN therefore uses one realistic week, which captures all
  `3,382` naive queries.
- EXPLAIN ANALYZE uses the literal SQL captured from both services. The old hand-written
  multiplying-join query was deleted because it did not match what either service issues.
